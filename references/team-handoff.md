# 团队仓库与两次交接

适用于一人定方案、另一人在自己的电脑与 Codex 上做实验，再由写作者独立接手。用一个竞赛研究仓库跟踪本队选定的题目。skill 的安装目录用于读取方法和工具，研究成果放进团队仓库。

## 仓库和版本对齐

已有团队仓库先克隆；只有建新仓库时才运行 `python3 <skill>/scripts/init_project.py <新目录> --title "研究题目" --team`。可用 `--problem <文件>` 加入可共享的题面。研究根目录保留导航与当前交接点（`README.md`）、机器可读阶段（`project.json`）和四个工作目录；`tools/` 随仓库提供检查工具。

| 阶段 | 工作位置 | 记录的版本 |
| --- | --- | --- |
| 设计 | `design/` | 题目拆解、来源、选定方案和完整实验协议；确认一版即提交 |
| 执行 | `experiment/` | 脚本、原始输入、各运行配置与输出、整理结果；六张证据表统一放在 `records/` |
| 报告 | `report/` | 已接受结果的独立快照、验证、复现与写作材料；由实验负责人整理 |
| 论文 | `paper/` | 提纲、可编辑正文、引用/排版资源和经过检查的最终稿 |

每次会话先核对远端地址、分支、工作区状态和上次交接的提交。两位负责人各自克隆同一研究仓库；工作区干净后用 `git fetch origin` 和 `git pull --ff-only` 接收更新。分叉或有本地修改时先保留双方工作，明确合并点，再接着实验。设计、脚本、输入版本或接受标准有变，记录变更理由和需要重做的运行，更新受影响的报告后再使用。

把一次确认的设计决定、首个有效基线、一批工况（含失败/中断）、一次改变结论的验证、报告或论文的一次可审阅修改作为保存点。当场更新文件、研究表和根目录的下一步，检查 diff 并选择本次文件提交。在团队指定且获准同步的远端推送；公开仓库只跟踪可公开的材料。离线时记录本地提交和待推送状态。用 `git rev-parse HEAD` 和 `git ls-remote origin refs/heads/<分支>` 比较完整提交号后发交接信息。报告记录它所依据的上游提交，报告自身的提交号在提交后交给接手人。

## 第一次交接：设计 → 实验

设计负责人填写 [方案入口](../assets/team/design/README.md)、[题目与要求](../assets/team/design/problem.md)、[模型与参数](../assets/team/design/model.md) 和 [实验协议](../assets/team/design/protocol.md)。把讨论中影响结果的选择、理由和边界直接写入报告。开放问题要区分“开工前必须解决”和“由实验判别”，后者给分支条件。

接手人在干净目录只读方案包，逐项检验：

1. 能复述题目输出、单位、评价标准，找全方程、假设、初边值以及输入来源。
2. 能从约定工作目录执行最小工况。代码若待实现，按接口、伪代码、参数与测试向量完成第一个实现步骤，不需要猜模型或询问原作者。写明已实测或仍待实现的部分。
3. 能说出输出应出现在哪里、预期数值或范围、怎样判定通过、失败先检查什么，也能按工况表继续剩下的实验。任何必需文件、权限或建模决定缺失，就在入口标为草稿并指出缺口。

将冷启动检查结果及执行者写进入口。接受后固定方案版次、提交并同步，在约定研究仓库的 `experiment/` 继续。实验表中的要求、来源、参数沿用方案 ID；同一工况的重新运行保留独立运行 ID。

## 第二次交接：实验 → 写作

实验负责人填写 [总报告入口](../assets/team/report/README.md)、[实际方法](../assets/team/report/methods.md)、[结果与讨论](../assets/team/report/results.md)、[复现步骤](../assets/team/report/reproduction.md) 和 [来源](../assets/team/report/references.md)。按已冻结的一批运行填报。将必要内容复制或导出到包内，保留上游提交、运行 ID 和原始数据定位；实验工作区仍保存原始记录。方案中计划做、实际未做的部分明确列为缺口。

- **给写作者**。完整复述题意、已知条件和问题要求，交代研究动机、选型、真实方法、符号和参数。每个问题对应可采用的结论、数值/单位/误差含义、条件与局限、主张 ID、运行或推导 ID、验证 ID，以及包内数据的表行/列或图号。给出主图成品、绘图数据、图注、实际核实的完整引文及支持内容。
- **给复现者**。提供运行过的入口及本地依赖、配置、所需输入、实际版本与设置、运行和重画命令、期望输出与容差。输入、代码或采集步骤不能只存在于某人的电脑。大型或受限数据给不可变版本、合法取得方式、大小与校验值；由接手方核对可访问性。写作需要的数表、图及方法必须在包内。解析或实测研究可交推导、采集/校准和处理协议，注明能够复现到哪一步。
- **验收**。只把总报告目录或 ZIP 给新会话，不附原仓库、聊天或独立题面。让它写出含带单位主结论的一段摘要、一条图注/主表说明，追溯到包内证据，并从独立目录复核一项代表结果。缺少核心证据、关键输入不可得、需要猜测参数或引用时，将缺口交回负责人。确实有依据的条件结果可以带条件写进论文。

## 检查与发送

1. 在两个包的 `materials.csv` 中登记附件，表头为 `path,role,description`，路径相对各自的包根。固定报告章节自动随包；分册、代码依赖、输入、图、表、验证输出都逐项列入。角色可用 `section`、`source`、`input`、`environment`、`figure` 等。总报告至少含 `code` 或 `method`、`result` 或 `table`、`validation` 三类真实附件。长内容按模型、工况或主张拆文件，入口保留短摘要与阅读顺序。使用包内相对 Markdown 链接或外部文献 HTTPS/DOI 链接。
2. 从研究仓库根运行以下命令。Windows 可将 `python3` 换成 `py -3`。选择当前交接所需的命令即可。

   ```text
   python3 tools/handoff.py design design
   python3 tools/handoff.py report report --zip exports/report-v1.zip
   python3 tools/handoff.py report <解压后的报告目录>
   ```

   任一种包都可通过 `--zip <新文件>` 导出。导出仅含固定章节、附件清单、列出的文件及 SHA-256 校验清单。压缩包解到空目录，重查时会同时校验文件字节。发送整个目录也可以。脚本会指出模板待填项、缺失文件、缺失附件类型或未随包交付的 Markdown 链接。外部资源可访问性、命令在接手机器上的表现和物理可信度需要实际检验。
3. 交接消息给出研究仓库、分支、完整提交号、入口和下一步。整个项目的严格交付检查仍使用 `tools/audit_project.py .`。交接通过表示该阶段可接手，论文交付还需独立核对研究证据与稿件。
